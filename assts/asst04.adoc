= GDB


== Where did the points go?

`scores.c` should add all four scores. Predict the correct total, then compile and run it:

[source, subs="quotes"]
----
gcc -std=c11 -Wall -Wextra -g -O0 scores.c -o scores
./scores
gdb ./scores
----

`-g` includes debugging information. `-O0` disables optimization to keep stepping through source straightforward.

At the GDB prompt, enter:

[source, subs="quotes"]
----
break sum_scores
run
print count
print scores[0]
next
----

A breakpoint pauses execution when the program reaches a location. `next` executes the current source line, 
stepping over any function calls. The displayed source line is normally the line about to execute, not a line 
that has already executed.

Continue with `next` until you are paused on `total += scores[i];`. Then inspect:

[source, subs="quotes"]
----
print i
print scores[i]
print total
next
print total
----

Keep stepping and inspecting until you understand the incorrect result. You can use `list` to see 
nearby source lines and `continue` to finish the run. `quit` exits GDB.

Answer the following questions in a text file:

1. What total did you expect, and what total did the original program print?
2. What index and score did the program use on its first addition? Include the GDB commands and values you observed.
3. Explain the bug. Fix it, exit GDB, recompile, and run again.
4. Give a second input array and its expected total. Change the data in `main` and check your fix, keeping the count consistent.

Submit your corrected `scores.c` and text file with your answers to the questions above.

== Why didn't the swap stick?

`swap.c` is supposed to exchange `first` and `second` in `main`. The message inside `swap` looks promising, but the 
final output is wrong.


[source, subs="quotes"]
----
gcc -std=c11 -Wall -Wextra -g -O0 swap.c -o swap
./swap
gdb ./swap
----


[source, subs="quotes"]
----
break swap
run
print left
print right
bt
----

`bt` (backtrace) lists the active function calls. You should see `swap`, called by `main`. 
You do not need to interpret addresses.

Use `next` to execute the assignments one at a time. Inspect `temporary` after its initialization, and `left` 
and `right` as the assignments execute. Remember: the highlighted line is normally about to execute. 
A local variable is meaningful only after its initialization has executed.

Once both assignments have executed, inspect:

[source, subs="quotes"]
----
print left
print right
finish
print first
print second
----

`finish` runs until the current function returns to its caller. You are now back in `main`, where `first` 
and `second` are in scope. Use `continue` to finish the program, then `quit` to exit GDB.

Answer the following questions in a text file:

1. What values should `first` and `second` have after a successful swap? What values does the original program print?
2. Record the values of `left` and `right` at function entry and after the assignments. Include the GDB commands you used.
3. After `finish`, what values do `first` and `second` have? Explain why changing `left` and `right` did not change them.
4. Fix `swap` so that it modifies the caller's variables. You will need to change the parameter types, the function body, and the call in `main`.
5. Recompile and rerun. Then use GDB to verify your correction. With pointer parameters, inspect `*left` and `*right` inside `swap`.
6. Test a second pair of values and explain what `bt` and `finish` helped you see.

Hint if needed: What should a function receive if it needs to modify an existing variable that belongs to its caller?

Submit your corrected `swap.c` and text file with your answers to the above questions.

= Valgrind

== Correct-looking output, incorrect memory use

`squares.c` allocates space for four integers and should print their squares: 0 1 4 9. It contains two memory-management bugs.

[source, subs="attributes"]
----
gcc -std=c11 -Wall -Wextra -g -O0 squares.c -o squares
valgrind --leak-check=full ./squares
----

Start with the first invalid-access report. Find the reference to your own file, rather than trying to 
understand every line of library output.

Answer the following questions in a text file:

1. Does Valgrind report an invalid read or an invalid write? Which source line caused it?
2. Which indices fit in the allocation? Which index causes the invalid access?
3. Fix that bug, recompile, and rerun Valgrind.
4. Find the remaining leak report. What allocation has no matching deallocation?
5. Fix the leak, recompile, and rerun Valgrind again. Confirm that it reports no invalid accesses and no leaked blocks from this program.
6. Explain why seeing the expected printed numbers would not prove that this program manages memory correctly.
